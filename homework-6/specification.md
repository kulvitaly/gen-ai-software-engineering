# FinTech Transaction Processing Pipeline Specification

> Ingest the information from this file, implement the Low-Level Tasks, and generate the code that will satisfy the High and Mid-Level Objectives.

## High-Level Objective

- Build a file-based transaction processing pipeline that ingests a JSON batch of financial transactions, validates each one, scores it for fraud, and reports a per-transaction and aggregate result, exposed through a small local dashboard.

## Mid-Level Objectives

- **Validation:** every transaction in the input batch is checked against a strict schema and business rules; *all* failures (not just the first) are collected per record, and any failing record is short-circuited straight to a terminal `rejected` result with human-readable reasons.
- **Fraud detection:** every record that passes validation is scored with an additive, auditable rule set (high-value, off-hours, cross-border, structuring/near-threshold); the score maps deterministically to a decision (`approved` / `flagged` / `blocked`), and the fired rules are recorded as reasons.
- **Reporting:** every transaction reaches exactly one terminal status (`rejected` / `blocked` / `flagged` / `approved`) written to `shared/results/`, plus a single run summary (counts per status, and the reasons behind rejections/flags/blocks) written to `shared/results/summary.json`.
- **Orchestration:** a single command seeds the pipeline from `sample-transactions.json`, drives validation → fraud detection → reporting in sequence, and is idempotent (each re-run reflects only the latest batch in `results/`) while the audit trail itself is never deleted.
- **Operability:** a minimal FastAPI + vanilla JS dashboard lets an authenticated operator trigger a run and see live per-transaction and aggregate results, without leaking internal error detail.

### File-based pipeline protocol (directory contract)

```
shared/
├── input/       ← orchestrator drops one JSON envelope file per transaction here
├── processing/  ← a stage moves a record here while working on it
├── output/      ← a stage writes its result here for the next stage to pick up
├── results/     ← terminal outcomes land here, one JSON file per transaction, plus summary.json
└── audit/       ← append-only audit log: audit.log (JSONL, one entry per line)
```

`shared/` is a runtime artifact — it does not exist in the beginning context and MUST be excluded from version control.

**Standard envelope** (one JSON file per transaction in `input/`/`processing/`/`output/`):

```json
{
  "message_id": "3fae7b9e-1234-4a11-9c2f-000000000001",
  "timestamp": "2026-03-16T09:00:00Z",
  "source_stage": "orchestrator",
  "target_stage": "validator",
  "message_type": "transaction",
  "data": {
    "transaction_id": "TXN001",
    "timestamp": "2026-03-16T09:00:00Z",
    "source_account": "ACC-1001",
    "destination_account": "ACC-2001",
    "amount": "1500.00",
    "currency": "USD",
    "transaction_type": "transfer",
    "description": "Monthly rent payment",
    "metadata": {"channel": "online", "country": "US"},
    "origin_country": "US",
    "status": "pending"
  }
}
```

- `message_id` is a fresh `uuid4` string generated by the orchestrator per transaction and used as the audit **trace/correlation id** end to end.
- `data` carries every field from `sample-transactions.json` **unchanged**, plus two fields the orchestrator adds when seeding: `origin_country` (copied from `data.metadata.country`) and `status` (`"pending"` initially; raw input never has a status).
- `source_stage`/`target_stage` are updated by each stage as the record moves forward (`orchestrator→validator`, `validator→fraud_detector`, `fraud_detector→report`).

### Validation rules (`pipeline/validator.py`) — pinned, no ambiguity

A Pydantic v2 model (`TransactionInput`) plus custom validators MUST enforce all of the following. Collect **every** violation (do not stop at the first) and return them as a list of human-readable strings.

| # | Rule | Failure message pattern |
|---|------|--------------------------|
| 1 | All of `transaction_id`, `timestamp`, `source_account`, `destination_account`, `amount`, `currency`, `transaction_type`, `description`, `metadata.channel`, `metadata.country` MUST be present | `"missing required field '<field>'"` |
| 2 | `transaction_id` matches `^[A-Za-z0-9_-]{1,64}$` | `"transaction_id '<value>' has an invalid format"` |
| 3 | `timestamp` parses as ISO 8601 UTC (`...Z` or `+00:00` suffix) | `"timestamp '<value>' is not a valid ISO 8601 UTC timestamp"` |
| 4 | `source_account` and `destination_account` each match `^ACC-\d{4,}$` | `"<field> '<value>' has an invalid account identifier format"` |
| 5 | `source_account != destination_account` | `"source and destination account must differ"` |
| 6 | `amount` parses to `Decimal` | `"amount '<value>' is not a valid decimal number"` |
| 7 | `Decimal(amount) > Decimal("0")` (applies to every `transaction_type`, including `refund` — the ledger convention is that `amount` is always a positive magnitude; direction is carried by `transaction_type`, not sign) | `"amount must be greater than 0 (got <value>)"` |
| 8 | `Decimal(amount) <= Decimal("1000000000")` | `"amount exceeds the maximum allowed value of 1,000,000,000"` |
| 9 | `currency` (uppercased) is one of the embedded **ISO 4217** set below | `"currency '<value>' is not a supported ISO 4217 code"` |
| 10 | `transaction_type` is one of `{"transfer", "wire_transfer", "refund"}` | `"transaction_type '<value>' is not supported"` |
| 11 | `description` is a non-empty string, ≤ 500 characters after trimming, and contains no ASCII control characters (defends against log/HTML injection) | `"description exceeds 500 characters"` / `"description contains invalid control characters"` |
| 12 | `metadata.channel` is one of `{"online", "branch", "api", "mobile"}` | `"metadata.channel '<value>' is not supported"` |
| 13 | `metadata.country` (uppercased) is one of the embedded **ISO 3166-1 alpha-2** set below | `"metadata.country '<value>' is not a supported ISO 3166-1 alpha-2 code"` |

**Embedded ISO 4217 currency set** (exact list to hard-code as a constant, e.g. `SUPPORTED_CURRENCIES`):
`USD, EUR, GBP, JPY, CHF, CAD, AUD, NZD, CNY, HKD, SGD, INR, BRL, MXN, ZAR, SEK, NOK, DKK, PLN, CZK, HUF, TRY, RUB, KRW, AED, SAR, ILS, THB, IDR, NGN`

**Embedded ISO 3166-1 alpha-2 country set** (exact list, e.g. `SUPPORTED_COUNTRIES`):
`US, CA, MX, GB, DE, FR, ES, IT, NL, BE, IE, PT, CH, AT, SE, NO, DK, FI, PL, AU, NZ, JP, SG, IN, NG, ZA, BR`

Any record failing one or more rules gets `status="rejected"` and is written directly to `shared/results/<transaction_id>.json` with `"reasons": [<all failure strings>]`; it MUST NOT be passed to the fraud stage.

**Duplicate transaction IDs:** the orchestrator (not the validator) checks `transaction_id` uniqueness while seeding the batch. The second and any later record sharing a `transaction_id` already seen in the same batch is written straight to `shared/results/` as `status="rejected"`, `reasons=["duplicate transaction_id in input batch"]`, and is not sent through validation.

### Fraud detection rules (`pipeline/fraud_detector.py`) — pinned, no ambiguity

Compute an integer score by summing every rule that fires; record each fired rule's message in `reasons`.

| Rule | Condition | Points | Reason message pattern |
|------|-----------|--------|--------------------------|
| High-value | `Decimal(data.amount) >= Decimal("10000.00")` | +2 | `"high-value transaction: amount <amount> <currency> >= 10000.00"` |
| Off-hours | UTC hour of `data.timestamp` is in `00:00:00`–`05:59:59` inclusive | +1 | `"off-hours transaction at <timestamp> UTC"` |
| Cross-border | `origin_country != destination_country` (see lookup below) | +2 | `"cross-border transfer: <origin_country> -> <destination_country>"` |
| Structuring (near-threshold) | `Decimal("9000.00") <= Decimal(data.amount) < Decimal("10000.00")` | +2 | `"amount just below the high-value reporting threshold (possible structuring): <amount>"` |

**Decision mapping** (total score → `status`): `0–1` → `approved`; `2–3` → `flagged`; `>= 4` → `blocked`.

`origin_country` = `data.origin_country` (already set by the orchestrator from `metadata.country`, already ISO-3166-validated).

`destination_country` is derived from `destination_account` via an embedded constant lookup table `DESTINATION_COUNTRY_MAP` (this simulates a destination-bank/country registry; it is a pipeline-internal business rule, not a public standard):

```python
DESTINATION_COUNTRY_MAP = {
    "ACC-2001": "US",
    "ACC-3001": "US",
    "ACC-9999": "US",
    "ACC-5500": "DE",
    "ACC-6600": "NG",
    "ACC-7700": "US",
    "ACC-8800": "GB",
    "ACC-9900": "US",
}
```

If `destination_account` is not a key in `DESTINATION_COUNTRY_MAP`, default `destination_country = origin_country` (treat as domestic rather than guessing a false cross-border signal).

`blocked` is terminal: write straight to `shared/results/<transaction_id>.json` with `status="blocked"`, `score`, and `reasons`. `approved` and `flagged` records pass to the reporting stage carrying `score` and `reasons`.

### Reporting stage (`pipeline/report.py`)

- Writes the terminal record (whatever `status` it receives — `approved` or `flagged` from the fraud stage, or `rejected`/`blocked` records that were already short-circuited by earlier stages) to `shared/results/<transaction_id>.json`.
- After all records in a run reach `shared/results/`, writes `shared/results/summary.json`:
  ```json
  {
    "generated_at": "2026-03-16T10:20:00Z",
    "total": 8,
    "counts_by_status": {"approved": 3, "flagged": 2, "blocked": 1, "rejected": 2},
    "rejected_reasons": ["currency 'XYZ' is not a supported ISO 4217 code", "amount must be greater than 0 (got -100.00)"],
    "flagged_reasons": ["high-value transaction: amount 25000.00 USD >= 10000.00", "amount just below the high-value reporting threshold (possible structuring): 9999.99"],
    "blocked_reasons": ["high-value transaction: amount 75000.00 USD >= 10000.00", "cross-border transfer: US -> NG"]
  }
  ```
- Also owns a GDPR erasure hook, `erase_transaction_record(transaction_id)`: deletes `shared/results/<transaction_id>.json` if present and appends a tombstone audit entry (`action="erase"`); returns `True`/`False` for found/not-found. This is the technical mechanism satisfying the Constitution's "right to be forgotten" for records already at rest in `results/`.

### Expected outcome on `sample-transactions.json` (worked example — implementers and testers MUST reproduce these exact results)

| transaction_id | outcome | why |
|---|---|---|
| TXN001 | `approved`, score 0 | 1500.00 USD, domestic (US→US), daytime — no rule fires |
| TXN002 | `flagged`, score 2 | 25000.00 USD ≥ 10000 → high-value (+2) |
| TXN003 | `flagged`, score 2 | 9999.99 USD is in the structuring band `[9000, 10000)` (+2) — deliberately just under the high-value threshold |
| TXN004 | `approved`, score 1 | 02:47 UTC is off-hours (+1); DE→DE is domestic; single weak signal alone does not flag |
| TXN005 | `blocked`, score 4 | 75000.00 USD → high-value (+2); US→NG → cross-border (+2) |
| TXN006 | `rejected` | currency `"XYZ"` is not in the supported ISO 4217 set — fails validation, never reaches fraud detection |
| TXN007 | `rejected` | amount `-100.00` is not `> 0` — fails validation (refunds still carry a positive magnitude) |
| TXN008 | `approved`, score 0 | 3200.00 USD, domestic, daytime — no rule fires |

Resulting `summary.json.counts_by_status`: `{"approved": 3, "flagged": 2, "blocked": 1, "rejected": 2}`, `total: 8`. Every one of the four terminal statuses is exercised by the sample data.

### Orchestrator (`orchestrator.py`)

- On each run: **clears and re-creates** `shared/input/`, `shared/processing/`, `shared/output/`, `shared/results/` (idempotent — `results/` always reflects only the latest run). `shared/audit/audit.log` is **never cleared or truncated by the orchestrator** — it is append-only across runs, satisfying Constitution Principle III (audit logs must not be deleted by application-level actors). If `shared/audit/` does not yet exist, create it empty.
- Reads `sample-transactions.json`, de-duplicates by `transaction_id` (writing duplicates straight to `results/` as `rejected` per the rule above), wraps each remaining raw record in the standard envelope with a fresh `uuid4` `message_id`, sets `data.origin_country = data.metadata.country`, `data.status = "pending"`, and writes one file per transaction into `shared/input/`.
- Runs the three stages in order (`validator.run` → `fraud_detector.run` → `report.run`), each stage reading its input directory, moving the record to `processing/` while working, and writing to the next stage's directory or to `results/` if terminal.
- Polls `shared/results/` until every seeded transaction has a terminal record, then prints a summary (counts per status) to stdout and returns it as a dict for programmatic callers (e.g. the frontend).

### Frontend (`frontend/`)

- **FastAPI + uvicorn** app at `frontend/app.py` serving:
  - `POST /run` — triggers `orchestrator.run_pipeline()`; returns `{"status": "ok", "summary": {...}}` on success.
  - `GET /results` — reads `shared/results/` and returns `{"total": N, "counts_by_status": {...}, "transactions": [{"transaction_id", "status", "score", "reasons"}, ...]}`.
  - Both endpoints are **non-public** and require a header `X-API-Key` matching the environment variable `PIPELINE_API_KEY` (never hardcoded, never logged); missing/invalid key → `401 {"detail": "unauthorized"}` with no further internal detail leaked. Any unhandled error → `500 {"detail": "internal error"}` (no stack trace, no file paths, no secrets in the body).
- Static dashboard at `frontend/static/index.html` (+ `app.js`, `styles.css`): a "Run pipeline" button (calls `POST /run`), an API-key input field kept only in browser memory (never embedded in the shipped JS), a counts tile row (approved/flagged/blocked/rejected), and a per-transaction table (`transaction_id`, status, score, reasons) that polls `GET /results` after a run. All dynamic text (description-derived reasons, ids) MUST be inserted via safe DOM APIs (`textContent`, not `innerHTML`) to prevent XSS.
- TLS note: local `uvicorn` runs over plain HTTP for this exercise; a production deployment MUST terminate TLS 1.2+ in front of it (documented as an explicit local-dev scope limitation, not a silent gap — call this out in `HOWTORUN.md` and it will be repeated in `docs/compliance.md` by the documentation agent).

### Audit logging (Constitution III) — pinned format

Every stage (`validator`, `fraud_detector`, `report`, `orchestrator`) appends one JSON line to `shared/audit/audit.log` per action:

```json
{"timestamp": "2026-03-16T09:00:01Z", "message_id": "3fae7b9e-...", "trace_id": "3fae7b9e-...", "actor": "system:validator", "stage": "validator", "action": "validate", "transaction_id": "TXN001", "decision": "validated", "amount": "1500.00", "currency": "USD", "masked_source_account": "ACC-**01", "masked_destination_account": "ACC-**01", "reasons": []}
```

- `masked_source_account`/`masked_destination_account` use `mask_account_id(acc)`: strip the `ACC-` prefix, replace every digit except the last two with `*`, re-prefix with `ACC-` (e.g. `"ACC-1001"` → `"ACC-**01"`).
- `description` is **never** written to the audit log (free-text field, potential personal data — Constitution II/III).
- For the two `POST /run` / `GET /results` audit entries emitted by the frontend, `actor` is `"operator"` (the authenticated caller) rather than `"system:<stage>"`.
- The log is append-only; no stage or endpoint may rewrite or delete existing lines (only `erase_transaction_record`'s tombstone entry and the record deletion in `results/` implement erasure, and that tombstone itself is appended, never overwriting prior lines).

### Data protection & GDPR notes (Constitution II)

- **Classification:** `source_account`/`destination_account` = pseudonymous financial identifiers (Financial data); `amount`/`currency`/`transaction_type` = financial data; `metadata.country`/`origin_country`/`destination_country` = derived location data. The schema carries no direct identifiers (no names, no card PANs, no national IDs, no special-category data).
- **Lawful basis:** processing is necessary to execute the payment instruction the data subject (account holder) initiated — Art. 6(1)(b) GDPR, contractual necessity. This applies to the synthetic dataset used here and is the basis that would carry to a production deployment with real accounts.
- **Minimization:** only the fields in the schema above are collected; `description` is capped at 500 characters and never copied into the audit log.
- **Data subject rights:** *access* — `GET /results` and the MCP tool `get_transaction_status` (already implemented, unchanged) return a transaction's current state by id; *erasure* — `pipeline.report.erase_transaction_record(transaction_id)` deletes the terminal record and tombstones the audit trail; *rectification/portability* are out of scope for this exercise (no mutable customer profile exists) and this is a documented, justified scope limitation, not a silent gap.
- **Retention:** for this local demo, `shared/results/` holds only the latest run (superseded on each `orchestrator` run); `shared/audit/audit.log` accumulates for the life of the local working copy. A production deployment would additionally enforce a documented retention period (this spec proposes 90 days for `results/`-equivalent transaction records and 7 years for the audit trail, matching common financial record-keeping norms) via a scheduled purge job — out of scope to implement here, but documented so the requirement is traceable.

## Constitution Check

- **I. Security by Design (NON-NEGOTIABLE) — satisfied within stated scope.** Both dashboard endpoints require `X-API-Key` (deny-by-default; the key is sourced from the `PIPELINE_API_KEY` environment variable, never committed or logged). All external input (the JSON batch and any HTTP body) is validated by Pydantic before use; the dashboard renders all dynamic values via `textContent` to prevent XSS; error responses never leak stack traces or paths. **Documented deviation:** the local `uvicorn` dev server does not itself terminate TLS; this is called out explicitly in `HOWTORUN.md`/`docs/compliance.md` as a local-exercise scope limit, with the production requirement (TLS 1.2+ termination in front of uvicorn) stated. SAST/dependency scanning are CI-level gates outside this local exercise's runtime and are not waived, only not executable in this offline context.

Data Protection & GDPR (NON-NEGOTIABLE) — satisfied.** Data minimization is enforced by the closed schema; fields are classified in the "Data protection & GDPR notes" section; lawful basis (contractual necessity) is documented; access (`GET /results`, MCP `get_transaction_status`) and erasure (`erase_transaction_record`) are technically actionable, not manual-only; retention is documented (results = latest run only; audit = life of the working copy, with a stated production retention target).

# /run-pipeline — run the transaction pipeline end-to-end

Execute the existing transaction processing pipeline against `sample-transactions.json`
(or an input file the user names) and report the outcome. This command **runs** the
already-built pipeline — it does not regenerate code, tests, or docs. Do all work from the
repo root.

Use the repo virtual environment interpreter for every Python invocation:
`.venv\Scripts\python.exe` (POSIX: `.venv/bin/python`). If `.venv` does not exist, create it
(`python -m venv .venv`) and install deps (`.venv\Scripts\python.exe -m pip install -r requirements.txt`)
before running.

Run these steps **in order**, stopping and surfacing the problem to the user if a
precondition fails:

## 1. Check the input file exists
- Confirm `sample-transactions.json` exists at the repo root and is a non-empty JSON array.
  (If the user passed a different path as an argument, check that instead.)
- If it is missing or unreadable, **STOP** and tell the user — do not run against a
  missing/empty input.

## 2. Clear the `shared/` staging directories
- Remove the runtime staging tree so the run starts clean: delete `shared/` (it is
  regenerated by the orchestrator). Use `Remove-Item -Recurse -Force shared` (PowerShell)
  or `rm -rf shared` (Bash). This is safe — `shared/` is gitignored, transient output.
- Do **not** touch `sample-transactions.json`, source code, tests, or docs.

## 3. Run the pipeline
- Run `.venv\Scripts\python.exe orchestrator.py`.
- It must exit 0. If it exits non-zero, **STOP** and surface the full stderr/traceback to
  the user — do not fabricate a summary.

## 4. Show a summary of results
- Read `shared/results/summary.json` and the per-transaction files in `shared/results/`.
- Present a concise summary: the total transaction count and the count per terminal status
  (`approved` / `flagged` / `blocked` / `rejected`), plus a short per-transaction
  table (transaction id → status). Confirm the counts sum to the number of input records.

## 5. Report rejected (and blocked) transactions with reasons
- For every transaction whose status is `rejected` — and call out `blocked` (fraud) ones
  too, since both are non-approved terminal outcomes — list its transaction id and the
  `reasons` recorded in its result file (e.g. validation failures for `rejected`, fraud
  rule hits for `blocked`).
- If there were none, say so explicitly.

## Final output
Print a short, skimmable report: input file used, per-status counts, the transaction table,
and the rejected/blocked detail with reasons. Keep it terminal-friendly. Report failures
faithfully with the real command output — never claim success the run did not produce.
